# hyperbee-rs

A Rust port of the npm `hyperbee2` B-tree (reference version 2.21.4) on top of
[`hypercore-rs`](../hypercore-rs) and [`corestore-rs`](../corestore-rs).

The reader accepts every block type hyperbee2 2.21.4 reads (latest block type 1,
legacy block type 0 and bee1 compat blocks). The writer produces byte-identical
blocks to hyperbee2's default (`type 1`) writer for the same batch sequence,
including the same splits, merges, cohorts, value blocks and checkpoint/
invalidation fields.

## Usage

```rust
# async fn demo() -> Result<(), Box<dyn std::error::Error>> {
use corestore::Corestore;
use hyperbee::Bee;

let store = Corestore::open(std::path::Path::new("./db"))?;
let bee = Bee::open(&store, None).await?; // core name "bee"

let mut batch = bee.batch();
batch.put(&b"name"[..], &b"example"[..]);
batch.flush().await?;

let entry = bee.get(b"name").await?.unwrap();
assert_eq!(entry.value, &b"example"[..]);

let mut stream = bee.range(Default::default());
while let Some(entry) = stream.next().await? {
    println!("{:?}", entry.key);
}
# Ok(())
# }
```

## API

- `Bee::open(&Corestore, Option<[u8; 32]>)`: opens the core with that key, or
  the core named `bee`.
- `Bee::from_session(&Corestore, Arc<Session>)`: use an existing root session;
  `from_session_with_encryption` also selects encryption keys for other cores.
- `Bee::head() -> Option<Head>`: root block count and root core key.
- `Bee::get(&[u8]) -> Result<Option<Entry>>`.
- `Bee::range(RangeOptions) -> RangeStream`: `gt`, `gte`, `lt`, `lte`,
  `reverse`, `limit`; call `next()` until it returns `None`.
- `Bee::batch() -> Batch`: `put`, `del`, then `flush()`. Ops apply in call
  order; a put followed by a del in one batch leaves the key deleted.
- `Bee::checkout(Head)`, `snapshot()` and `move_to(Head)` select roots across
  cores; checkouts and snapshots are read-only.
- `Bee::cores(local)` lists the current core table; `false` excludes the local core.
- `Bee::changes(head, prefetch)` walks batches backwards, holding a cancellable
  download window; each change includes its head, tail and decoded blocks.
- `Bee::reindex(until, prefetch, map)` copies selected changes to the local
  core; `reindex_async` accepts a fallible asynchronous head predicate.
- `get_with_options`, `range_with_options` and `changes_with_options` accept
  Hypercore read options, including timeouts, wait and request bags.
- `Bee::close()` closes an owning bee's store; closing a view leaves it open.
- `Bee::update() -> Result<bool>`: move to the root core's latest block.

`Entry` carries the data block sequence number, key and value. Blocks that
reference other cores (the `metadata.cores` table) are resolved through the
same `Corestore`, as in the JS implementation.

## Compatibility notes

- Block codecs are generated by [`hyperschema-rs`](../hyperschema-rs) from
  `spec/hyperschema/schema.json`, copied from npm `hyperbee2 2.21.1`
  (`spec/hyperschema/schema.json`). Hand-written encoding code is limited to the
  block-type dispatch, the type 0 cohort conversion and the bee1 compat decoder.
- Block type 0 is decoded, including its cohort layout.
- Metadata frames written with schema version 1 are decoded with bounded frames.
- Bee1 `TYPE_COMPAT` (10) blocks are decoded.
- Only latest blocks are written. There is no API to request compat or type 0
  writes, matching the default hyperbee2 writer.
- Values larger than 1024 bytes are stored in separate value blocks exactly as
  hyperbee2 does; value pointers, offsets and block splitting follow the JS
  rules.
- The in-memory tree uses append-only arenas; the JS node cache's LRU eviction
  and its tuning knobs are not ported (nodes stay resident for the lifetime of
  the `Bee`).
- Encryption keys are currently attached to the physical core on first open;
  reopening a cached core with a different key cannot change its encryption.

## Not ported

- Diff streams (`createDiffStream`), `copy`, preload hooks, tracing and custom
  encryption providers beyond the encryption keys supported by hypercore.
- Node cache eviction/tuning, range prefetching, rollback (`unbatch`).
- Mappings can be read from block metadata, but there is no write API that
  supplies new mappings.

## Fixtures and tests

Generated fixtures live in `fixtures/`; `fixtures/gen/gen.js` writes them with
npm `hyperbee2 2.21.4`, `corestore 7.16.1` and `hypercore 11.40.3`:

```sh
cd fixtures/gen && npm install && node gen.js
```

- `tests/read_js.rs`: appends the reference blocks and compares `get` and
  range results with hyperbee2.
- `tests/write_js.rs`: replays every batch sequence and compares every appended
  block byte for byte.
- `tests/js_reads_rust.rs` (`#[ignore]`): Rust writes a fresh bee, a node script
  appends its blocks and prints hyperbee2's read stream for comparison. Run it
  with `cargo test -- --include-ignored` after `npm install` in `tests/js`.
- `fixtures/gen/completion.js` and `tests/completion.rs`: cross-core move,
  changes, core listing, reindexing and byte comparisons.
- `tests/moved_core.rs`: writes after moving onto a head on another core
  (`fixtures/moved-core.json`), pinning the cross-core relocation of the delta
  cohort pointer.
- `tests/smoke.rs`: single-key block byte check.

```sh
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test -- --include-ignored
```

Cold tree inflation shares decoded blocks within one node, then drops that
temporary cache. It never caches decoded blocks across forks or later reads.
Apply and lazy tree inflation still share the ordered tree-state lock; snapshots
share that arena too, so replacing it with a read lock would not make reads safe.

Cross-core context lookup stores weak references: live contexts retain their
identity, expired contexts reload by key, and dropping the last tree releases
its contexts and core sessions without requiring `store.close()`. The
`cross_core_contexts_close_with_the_last_bee` regression writes across two cores,
cold-opens the resulting tree, checks lookup identity and expired-entry reload,
then drops every bee. Retained shared owners, tracked contexts and sessions fell
from 2 / 1 / 2 to 0 / 0 / 0; the old strong context cache formed an ownership cycle.

`CATALOG_ENTRIES=10000 cargo test --release --test catalog_perf -- --ignored --nocapture`
measures three cold catalog lists plus point lookups in isolated synthetic stores
(32-entry batches, 256-byte values). Three-run release medians on Apple Silicon:

| Entries | List + lookup ms | Allocation calls | Allocated MiB | Process peak RSS MiB |
| --- | --- | --- | --- | --- |
| 552 | 6.842 → 1.275 | 26,455 → 5,161 | 38.2 → 3.3 | 17.2 → 11.8 |
| 560 | 6.774 → 1.248 | 26,762 → 5,230 | 38.4 → 3.4 | 17.3 → 11.8 |
| 10,000 | 182.788 → 18.932 | 546,968 → 88,495 | 880.4 → 67.7 | 139.2 → 37.8 |

For 10,000 entries the measured read-phase CPU fell from 0.18 to 0.02 seconds;
the small cases are below the 10 ms CPU-counter resolution. RSS includes fixture
construction, not just the read phase. These are library workloads, not a live
channel-follow or application text-search measurement. `CATALOG_WORKERS` selects
the runtime worker count (default 4).
